# M4 Billing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bill what the boutique makes, GST-correct and without staff needing to know GST: a price list with HSN/SAC and GST slabs; one tap "Create bill" from an order that fills in every garment, every chargeable rework/alteration and the advances already paid; bills issued with gapless numbers, an immutable snapshot and a clear PDF to print or share; payments, advances (receipt vouchers with GST for stitching services), refunds, credit notes and cancellations; month locks after filing; customer money and "money owed" derived from the documents; reminders and a daily collections summary; and an admin "check records" that proves nothing was tampered with.

**Architecture:** Same modular monolith. All tax arithmetic is pure, in `packages/shared/src/gst.js` (slab choice, place of supply, line and invoice-discount maths, rounding, tax on advances, credit notes), so the web previews exactly what the API will issue. Three new API modules: `catalog` (price list), `periods` (month locks — also used by expenses in M5) and `billing` (every money document, allocations, ledger, PDFs, billing notifications and jobs). Every money document (invoice, credit note, receipt, receipt voucher, refund) lives in one collection `billingDocuments` (Mongoose discriminators on `type`), so a customer's ledger, a register or an M8 tile is one indexed query. Money applied to bills is a separate append-only `allocations` collection of signed rows. Issued documents are immutable at the model layer; PDFs are rendered by the worker from the stored snapshot only, and their SHA-256 is recorded. Billing reads orders, garments, stage events, customers, branch and settings only through those modules' `service.js` exports.

**Tech Stack:** As M3, plus `pdfmake` 0.2.x (pure JS, server-side `PdfPrinter`) in `apps/api`, the Noto Sans TTF fonts (OFL) bundled in `apps/api/assets/fonts/`, and `fontkit` as an `apps/api` devDependency (one font test).

**Spec:** `docs/superpowers/specs/2026-10-22-vastrasanskara-system-design.md` — §5 (all), §2.6, §3.1 settings (`advancePercent`, `billDueDays`, `b2clThreshold`, `numberSeries`, `cancellationRefundSchedule`, `closingTime`), §4 (rework/alteration charges, rejected never charged), §8.1, §8.3 rows (order confirmed + advance, invoice issued, invoice overdue, daily collections summary), §8.4, §9.1 money tiles (data only — tiles are M8), §10.2, §10.3, §11 (`PERIOD_LOCKED`, `DOCUMENT_IMMUTABLE`, `ADVANCE_EXCEEDS_TOTAL`, idempotency, PDF failure), §12 (unit list, integration list, permission matrix). M3 ledger carried: `.superpowers/sdd/2026-10-25-m3-production/progress.md` — `stageEvents.chargeable`/`chargeAmount` (designers flag, front desk prices: "The front desk sets the amount when billing."), rejected garments never billed, remakes copy `agreedPrice`/`catalogItemId` and are billed normally.

## Global Constraints

- Everything in the M1–M3 Global Constraints still applies (integer paise, UTC + IST business-date strings, `branchId`, `version` in bodies and responses with 409 `CONFLICT`, strict zod, error shape, money stripping by key absence, no personal data in logs, bundled fonts/icons, 390 px screens, sentence case, plain words).
- Layout rule (user directive): each module keeps `model.js`, `service.js` (plus focused service files where a module is large, as `orders/garments.js`), `routes.js`, `jobs.js` in its own folder; one module never reads another module's models. Billing gets orders/garments only via `orders/service.js`, stage events only via `production/service.js`, items only via `catalog/service.js`, locks only via `periods/service.js`.
- **Every billing route needs at least `money.view`**; designers (no `money.view`) get 403 on every billing, catalog and period route. Write permissions: `billing.draft` (create/edit/delete drafts), `billing.issue`, `payments.record`, `discounts.give` (any non-zero discount), `billing.cancel` (cancel a bill, cancel a receipt, credit notes, refunds, pause reminders — admin only, see Decisions), `periods.lock`, `audit.verify`, new `catalog.manage` (admin only).
- **Idempotency:** `POST …/issue`, `POST /payments`, `POST /refunds`, `POST …/credit-notes` require `Idempotency-Key` (`idempotent()` after `validate`). After commit, the handler answers 2xx even if reading the document back fails (M2 `respondCommitted` pattern), so the key is never freed for a committed write.
- **Immutability:** an issued or cancelled document's number, date, snapshot, lines and totals never change. Only these paths may change after issue: `status` (`issued → cancelled`), `cancellation`, `pdf.*`, `settlement.*` (invoices), `remindersPaused`, `updatedAt`, `updatedBy`, `__v`. Anything else → model throws; services answer 422 `DOCUMENT_IMMUTABLE`. Drafts (invoices only) are freely editable and deletable.
- **Period locks:** every billing write checks `assertPeriodOpen(branchId, ymd, session)` inside its transaction, with `ymd` = the date of the document being created (today) or, for a cancellation, the original document's date → 422 `PERIOD_LOCKED` (`details: { month }`).
- **Dates:** every billing document is dated the IST day it is created (`istDate(clock.now())`, one clock read per transaction for both date and number); no back-dating. `month` = `date.slice(0, 7)`; `fyCode` = `financialYear(now).code`.
- **Numbers:** `<branch.prefixes[field]>/<fyCode>/<seq padded to 4>`, ≤ 16 characters, gapless per branch × type × FY, taken with `nextDocumentNumber` inside the issuing transaction; first number from `settings.numberSeries['<docType>:<fyCode>']`. Doc types and prefix fields: `invoice`→`invoice`, `credit_note`→`creditNote`, `receipt`→`receipt`, `receipt_voucher`→`receiptVoucher`, `refund`→`refund`.
- **Audit:** issue, cancel, credit note, receipt, receipt cancel, refund, reminder pause, catalog tax fields, period lock/unlock — each `recordAudit` in the same transaction; discount amounts and reasons are part of the issue entry.
- **Concurrency:** every transaction that changes a customer's money (issue, payment, receipt cancel, refund, credit note, bill cancel) first bumps that customer's money guard (`guardCustomerMoney`), so two at once conflict and the driver retries one against fresh data (same idea as M3 `stageSeq`).
- **Tax:** prices (agreed garment prices, catalog prices, line rates) are **before GST**; GST is added on the bill (see Decisions). Rates are integer basis points (`500` = 5 %). Tax per line in paise, half up; bill total rounded to the rupee with an explicit round-off.
- **Words in the UI:** "Bill" (not invoice), "Take payment", "Advance", "Money owed", "Receipt", "Refund", "Credit note (reduce a bill)", "Cancel bill", "Price list", "Month locks", "Check records". GST terms (HSN/SAC, CGST/SGST/IGST, place of supply) appear on the printed bill and in admin screens, not in the front-desk flow.
- Commit subjects end with `(M4 Task N)`. No deploy/infra changes.

## Decisions made in planning

| # | Decision | Why | Cost if wrong |
|---|---|---|---|
| 1 | **Prices are before GST** (tax-exclusive): an agreed price of ₹4,500 at 5 % bills ₹4,725. | GST slabs depend on the taxable value per piece; with tax-inclusive prices a price between ₹2,625 and ₹2,950 has no consistent slab. Exclusive keeps every bill exactly computable. The bill-from-order screen shows "GST will be added" beside the order value. | If the client quotes GST-inclusive prices, add an `inclusive` mode to `computeInvoice` (back-calculate taxable, rule for the slab gap) and a branch setting — about one task, no data migration (snapshots hold the figures). **Ask the client.** |
| 2 | The slab is chosen by the line's **taxable value per unit after line and bill discounts**. | GST is levied on transaction value; discounts given on the bill reduce it. | Accountant may say "before discount": one function argument in `selectSlabRate` callers. |
| 3 | **One `billingDocuments` collection** with discriminators (`invoice`, `credit_note`, `receipt`, `receipt_voucher`, `refund`); the spec's `payments` are `receipt` documents. | One ledger query, one immutability guard, one PDF queue, one integrity check, one index set for M8. | Splitting later is a data migration; reports would query by `type` either way. |
| 4 | **Allocations are their own append-only collection** of signed rows `{ paymentId, invoiceId | refundId, amount }`; releasing money is a negative row. (Spec: `payments.allocations[]`.) | Receipts stay immutable; allocation history is auditable; "unallocated advance" = receipt amount − Σ its rows. | Embedding later = migration; logic is in one file (`allocations.js`). |
| 5 | Invoices carry a **`settlement` cache** `{ advanceApplied, paid, credited, balance }` **recomputed from allocations and credit notes** (never incremented) in the same transaction as every change; "Check records" recomputes all and reports mismatches. Customer balances, ledger and ageing are fully derived (no stored running balance). | "Money owed" and M8 outstanding/overdue/ageing must not scan every invoice ever issued; a partial index on `balance > 0` makes them cheap. | If read as a "stored balance" against the spec: drop the field and aggregate allocations per invoice (queries in `ledger.js` only). |
| 6 | Bills, receipts, vouchers and refunds are **dated the day they are made**; no back-dating. | Keeps numbers in date order (GST) and makes the current month the only one new documents touch. | Late-entered cash shows the next day's date in the collections summary. A `receivedOn` note field covers it. |
| 7 | GST document prefixes are limited to 6 characters `[A-Z0-9-]` (order prefix keeps 10). Over 16 characters at issue → 422 `DOC_NUMBER_TOO_LONG`. | `ABCDEF/2627/0001` = 16 characters, the GST limit. | None (defaults are 2–4 characters). |
| 8 | **Garment → price-list item:** an item of kind `garment`/`stitching_service` lists the garment types it bills (`garmentTypes[]`); extra charges are items with `chargeFor: 'rush' | 'alteration' | 'rework'`. One active item per garment type and per `chargeFor`. `garment.catalogItemId` (if set) wins. | Orders already exist without item ids; staff should never pick HSN codes at the counter. | A missing mapping shows "Choose what to bill this as" on the line (issue refuses `ITEM_REQUIRED`). |
| 9 | **Advance for stitching services:** the service share of an order advance = advance × (estimated value with GST of the order's service lines ÷ the order's estimated total); a receipt voucher (RV) is issued for that share with GST backed out of the amount received. On the final bill, applied advance adjusts each RV in proportion to what was applied from its receipt; refunds reverse RV tax the same way. Advances with no order are treated as goods (receipt only). | Spec §5.5 requires RVs for service advances; proportional splitting is the only rule that needs no staff input. | Accountant to confirm (spec §15). The maths is isolated in `computeAdvanceTax` / `proportionalTax`. |
| 10 | Issuing a bill **automatically applies** advance held: first the order's receipts, then receipts with no order, oldest first; never another order's advance. | "Applies advances automatically" without stealing another order's advance. | Staff can't choose; a receipt cancel + re-take fixes a wrong one. |
| 11 | **Admin only** (`billing.cancel`): cancel bill, cancel receipt, credit notes, refunds, pause reminders; **`catalog.manage`** (new, admin only) for the price list. | Money out and tax corrections are owner/accountant decisions. | Operations need the owner for refunds; adding `refunds.give` to operations is one line in `permissions.js`. |
| 12 | A month can be **locked only after it has ended**; a lock is one document per (branch, month) with history. `assertPeriodOpen` also writes to that document when the date is in a past month, so a lock taken during such a write makes one of them retry. | Locking the running month would block today's bills; the write makes the lock/cancel race safe. | None. |
| 13 | Concurrent money writes for **one customer** are serialised with a guard document (`billingGuards`, `_id` = `<branchId>:<customerId>`, `$inc seq`). | Two payments or an issue and a payment at once could otherwise over-apply the same advance. | Throughput per customer is one write at a time (irrelevant at boutique scale). |
| 14 | The **PDF key is chosen at issue** (`<branchId>/billing_pdf/<yyyy>/<uuid>.pdf`, `pdf.status 'pending'`); the worker job `billing-pdfs` (every minute) renders it. Client emails with the PDF are queued in the issuing transaction with `notBefore = now + 2 min` (new `emit` option); if the PDF is still missing, delivery's normal retry waits for it. | Outbox stays in the business transaction (spec §8.1) while the PDF is rendered later (spec §5.3). | A PDF that never renders makes the email fail after its retries → visible on the admin outbox screen. |
| 15 | **Overdue reminders:** the client gets one email per bill per reminder (`invoice.overdue`, sequence n = 1…4: day after due, then +7, +14, +21); operations get **one daily digest** (`invoice.overdue_digest`) instead of one message per bill. Checked every 15 min once IST ≥ 10:00. | Spec §8.3/§8.4; per-bill staff messages would flood operations. | Template/rule change only. |
| 16 | **Payments above a bill's balance** keep the excess as advance (the dialog says so); `ADVANCE_EXCEEDS_TOTAL` applies to an **order advance** that would exceed the order's estimated total with GST; explicit over-allocation is impossible (the server allocates). | Customers round up; refusing would stall the counter. | — |
| 17 | **One draft bill per order**; "Create bill" on an order with a draft opens that draft. Credit notes have no drafts (issued from a dialog). | Prevents two half-made bills for the same garments. | — |
| 18 | Quantities allow 3 decimals (metres of fabric); units are GST UQC codes `PCS`, `MTR`, `SET`, `NOS`, `OTH`. | Material lines (spec §5.4 "garment plus separate material lines"). | — |
| 19 | A rush charge line is added to a bill-from-order only when the order is `rush` and a `chargeFor: 'rush'` item exists; chargeable stage events without an amount take the item's default price, else the line shows "Enter the price" and issue refuses `PRICE_NEEDED`. | Matches the M3 ruling "the front desk sets the amount when billing". | — |
| 20 | A bill with credit notes cannot be cancelled (`HAS_CREDIT_NOTES`); credit notes and refunds are corrected by new documents, never cancelled. A credit note for a financial year past its correction deadline (30 Nov after the FY) is allowed with a warning. | Keeps the document chain simple and reportable. | — |
| 21 | Receivables ageing buckets are **days past the due date**: `not_due`, `d0_30`, `d31_60`, `d61_90`, `d90_plus`. | Spec §9.2 buckets; due date is what staff chase. | Report-only change. |
| 22 | Phones: the bottom bar shows the **first four permitted** `bar` items; the rest move under More. Nav order Home, Orders, Bills, Customers, Production → front desk sees Bills, designers see Production. | Seven slots do not fit 390 px. | Nav order only. |
| 23 | **Share** fetches the PDF through its 5-minute signed link and calls the Web Share API with the file (falls back to download). | Staff send bills on WhatsApp from their phone without WhatsApp integration. | Needs CORS `GET` from the app origin on the files bucket at go-live (listed in Not in M4). |
| 24 | Once a series has issued a number in a financial year, changing its `numberSeries` start is refused (`SERIES_IN_USE`). | Changing it mid-year would create a gap or duplicate GST numbers (M2 ledger noted the jump). | — |

## Review Focus

1. **Double tap on "Issue bill", or an issue that fails half way** — exactly one number is used, the next bill gets the next number, no gaps. → Task 7 tests `issuing twice with one key returns the same bill` and `an aborted issue leaves no gap in the numbers`.
2. **Two payments for the same customer at the same moment, both landing on one bill** — the bill is never paid twice; the excess stays as advance; allocations sum to the receipts. → Task 8 test `two payments at once never over-pay a bill`.
3. **A locked month** — every billing write dated in it (issue, payment, refund, credit note, bill cancel, receipt cancel) is refused with 422 `PERIOD_LOCKED` and writes nothing (no number, no audit, no outbox). → Task 13 test `a locked month refuses every billing write`.
4. **Tampering** — an audit entry edited in the database, a stored PDF replaced, or a bill balance that disagrees with its payments is reported by "Check records" with the first break. → Task 13 tests `a changed audit entry is found`, `a replaced PDF is found`, `a balance that disagrees with its payments is found`.
5. **Advance for a stitching order, then a garment is rejected** — the advance gets a receipt and a receipt voucher with GST; the bill excludes the rejected garment, applies the advance and adjusts the voucher, never double-counting tax. → Task 8 test `the advance is applied when the bill is issued and the voucher is adjusted`; Task 7 test `a rejected garment cannot be billed`.

### Task 1: Shared — GST, billing helpers and state names

**Files:**
- Create: `packages/shared/src/gst.js`, `packages/shared/src/billing.js`, `packages/shared/src/states.js`
- Modify: `packages/shared/src/money.js`, `packages/shared/src/index.js`
- Test: `packages/shared/test/gst.test.js`, `packages/shared/test/billing.test.js`, `packages/shared/test/money.test.js`

**Interfaces:**
- Consumes: `allocateProRata`, `roundToRupee`, `amountInWords` (money.js); `financialYear`, `istDayBounds`, `addDaysYmd` (fy.js).
- Produces (`money.js`): `mulDivRound(a, b, c) → int` — `a × b ÷ c` rounded half away from zero, with BigInt (no float); throws on non-integers or `c ≤ 0`.
- Produces (`states.js`): `GST_STATES` (frozen map of the GST state codes `01`…`38` and `97` → name, e.g. `'29': 'Karnataka'`, `'97': 'Other Territory'`), `stateName(code) → string` (throws on unknown).
- Produces (`gst.js`), all pure:
  - `GST_RATES_BP = [0, 25, 150, 300, 500, 1200, 1800, 2800, 4000]`; `RULE46_ADDRESS_THRESHOLD = 5000000` (₹50,000).
  - `class GstError extends Error { code }` — codes `NO_LINES`, `DISCOUNT_EXCEEDS_LINE`, `DISCOUNT_EXCEEDS_TOTAL`, `BAD_SLABS`, `CREDIT_EXCEEDS_LINE`.
  - `selectSlabRate(gstSlabs, { taxable, qtyMilli }) → rateBp` — `gstSlabs = [{ upToUnitPrice: paise | null, rateBp }]` sorted ascending, exactly one `null` (last); the first slab with `taxable × 1000 ≤ upToUnitPrice × qtyMilli` (integer compare), else the `null` slab. Bad slabs → `BAD_SLABS`.
  - `placeOfSupply({ branchStateCode, customer: { gstin, stateCode } }) → { stateCode, stateName, interState, registered }` — registered (GSTIN) → GSTIN state; unregistered → `customer.stateCode` if set, else branch state; `interState = stateCode !== branchStateCode`.
  - `toMilli(quantity) → int` — `quantity` with ≤ 3 decimals → thousandths, via string parsing (as `rupeesToPaise`).
  - `computeInvoice({ lines, invoiceDiscount = 0, interState }) → { lines, totals, taxSummary }`. Input line `{ key, quantity, rate, discount = 0, gstSlabs, hsnSac? }`. Per line: `gross = mulDivRound(rate, qtyMilli, 1000)`; `discount ≤ gross` (else `DISCOUNT_EXCEEDS_LINE`); `invoiceDiscountShare` from `allocateProRata(invoiceDiscount, lines.map(gross − discount))` (`invoiceDiscount ≤ Σ` else `DISCOUNT_EXCEEDS_TOTAL`; skipped when 0 or every weight is 0); `taxable = gross − discount − share`; `rateBp = selectSlabRate(...)`; intra-state `cgst = sgst = mulDivRound(taxable, rateBp, 20000)`, `igst = 0`; inter-state `igst = mulDivRound(taxable, rateBp, 10000)`; `total = taxable + cgst + sgst + igst`. Output line = input `key`, `hsnSac` + `{ qtyMilli, gross, discount, invoiceDiscountShare, taxable, rateBp, cgst, sgst, igst, total }`. `totals = { gross, discount (line + bill), taxable, cgst, sgst, igst, tax, subtotal, roundOff, total }` with `roundToRupee(subtotal)`; `taxSummary = [{ hsnSac, rateBp, taxable, cgst, sgst, igst }]` grouped by `hsnSac` + `rateBp`, sorted. No lines → `NO_LINES`.
  - `computeAdvanceTax({ amount, parts: [{ weight, rateBp }], interState }) → { lines: [{ rateBp, gross, taxable, cgst, sgst, igst }], gross, taxable, cgst, sgst, igst, tax }` — `amount` is tax-inclusive; split by `allocateProRata(amount, weights)`; per part `t = mulDivRound(gross, 10000, 10000 + rateBp)`; intra `cgst = sgst = mulDivRound(t, rateBp, 20000)`, inter `igst = mulDivRound(t, rateBp, 10000)`; then `taxable = gross − tax heads` so every part sums exactly to its gross.
  - `proportionalTax({ part, whole, of: { gross, taxable, cgst, sgst, igst } }) → { gross, taxable, cgst, sgst, igst }` — `part === whole` returns `of` exactly; else each head `mulDivRound(head, part, whole)` and `taxable = gross − heads` (used for RV adjustment and reversal).
  - `computeCreditNote({ originalLines, credits: [{ key, taxable }], creditedSoFar: { [key]: taxable }, interState, full }) → { lines, totals }` — `full` copies every original line's figures and the original `roundOff` exactly (minus nothing; refused when anything was credited before); partial: each credit `taxable ≤ original.taxable − creditedSoFar[key]` (else `CREDIT_EXCEEDS_LINE`), tax at the original `rateBp` (same rounding as `computeInvoice`), totals rounded with `roundToRupee`.
  - `correctionDeadline(invoiceDateYmd) → ymd` — 30 November after the end of the invoice's financial year (`'2027-03-31'` → `'2027-11-30'`, `'2027-04-01'` → `'2028-11-30'`).
- Produces (`billing.js`):
  - `DOC_TYPES = ['invoice', 'credit_note', 'receipt', 'receipt_voucher', 'refund']`; `PREFIX_FIELD = { invoice: 'invoice', credit_note: 'creditNote', receipt: 'receipt', receipt_voucher: 'receiptVoucher', refund: 'refund' }`; `MAX_DOC_NUMBER_LENGTH = 16`.
  - `formatDocumentNumber(prefix, fyCode, n) → 'INV/2627/0001'` (pad 4, longer numbers grow); throws `RangeError` when longer than 16.
  - `daysBetween(fromYmd, toYmd) → int`.
  - `payStatus({ total, balance }) → 'paid' | 'part_paid' | 'unpaid'`.
  - `reminderSequence(dueDate, today) → 1..4 | null` — `d = daysBetween(dueDate, today)`; `d ≥ 1` → `1 + floor((d − 1) / 7)` while ≤ 4, else null.
  - `ageingBucket(dueDate, today) → 'not_due' | 'd0_30' | 'd31_60' | 'd61_90' | 'd90_plus'` (days past due: ≤ 0 not due; 1–30; 31–60; 61–90; > 90).
