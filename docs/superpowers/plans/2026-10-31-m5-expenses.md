# M5 Expenses Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record every rupee the boutique spends in about 20 seconds on a phone: "Add expense" asks for the amount, what it was for (category chips), who was paid (a vendor or any name), how it was paid and a photo of the bill. GST details are optional and folded away ("Has a GST bill?"); entering the total and the rate fills in the taxable value and the CGST/SGST or IGST split. Expenses get internal numbers `EXP/2627/0001` (gapless per financial year), respect month locks, are never deleted (voided with a reason) and every change is audited. The admin sees each month's total and its split by category; categories are edited in Settings. An expense can be linked to a garment, a batch or an order so M6 costing can use it; designers never see any of it.

**Architecture:** Same modular monolith. Tax arithmetic stays pure in `packages/shared` (`expenses.js` reuses `computeAdvanceTax`, `taxHeads` and `placeOfSupply` from `gst.js`), so the form previews exactly what the API stores. One new API module `expenses` (`model.js`, `service.js` for create/edit/void, `queries.js` for lists and month figures, `costing.js` for the M6 data function, `json.js`, `routes.js`). It reads vendors only via `vendors/service.js`, orders/garments/batches only via `orders/service.js`, locks only via `periods/service.js`, categories and number series only via `settings/service.js`, the branch only via `branches/service.js`. Bill photos use the M1 presigned upload flow with a new file purpose. Every month figure is one aggregate bounded by the `(branchId, date)` index, so M8 tile 10, the expense register and the input-tax side of GSTR-3B are reads of data this milestone already stores.

**Tech Stack:** As M4. No new dependencies (client-side photo shrinking uses the browser canvas).

**Spec:** `docs/superpowers/specs/2026-10-22-vastrasanskara-system-design.md` — §6.1 (all), §6.3 (expense cost: taxable value, plus GST when `itcEligible` is false; batch split equally — data only, screens are M6), §5.6 (expenses refused in locked months), §5.7 (expenses audited), §9.1 tile 10 and §9.2 expense register / GSTR-3B input tax (data shape only — M8), §10.2 (`expenses.write` admin + operations), §10.3 (uploads: JPEG, PNG, WebP, HEIC, PDF, 10 MB, presigned), §11 (`PERIOD_LOCKED`, idempotency, error shape), §12 (period lock refusals across every expense write; permission matrix). M4 ledger carried: `.superpowers/sdd/2026-10-30-m4-billing/progress.md` — `assertPeriodOpen` must run inside the transaction and also guards past months (Tasks 3–4 ruling); counters are held by `holdSeries` so a series-start change conflicts with a first number (Task 5 ruling, already covers `expense:<fy>`); the permission route table is hand-written but asserted equal to the routers' declared routes (Task 13 ruling); a write that has committed answers 2xx even if reading it back fails (`respondCommitted`).

## Global Constraints

- Everything in the M1–M4 Global Constraints still applies (integer paise, UTC + IST business-date strings, `branchId`, `version` in bodies and responses with 409 `CONFLICT`, strict zod, error shape, no personal data in logs, bundled icons, 390 px screens, sentence case, plain words).
- Layout rule (user directive): `apps/api/src/modules/expenses/` keeps `model.js`, `service.js`, focused service files (`queries.js`, `costing.js`), `json.js`, `routes.js`. No other module reads the `Expense` model; M6/M8 call `expenses/service.js` exports. The expenses module never imports another module's `model.js`.
- **Permissions:** new `expenses.view` (admin + operations) for every read; `expenses.write` (admin + operations, exists) for create, edit, void and the payee list. Designers have neither, so every `/v1/expenses` route answers them 403 and bill photos are "not found". Categories are edited through `/v1/settings` (`settings.edit`, admin only).
- **Period locks:** create checks `assertPeriodOpen(branchId, date, session)` for the expense date; edit checks the stored date and, when the date changes, the new date; void checks the stored date — all inside the write's transaction → 422 `PERIOD_LOCKED` (`details: { month }`), nothing written (no number, no audit).
- **Dates:** `date` is the day the money was paid (IST `YYYY-MM-DD`), default today, may be earlier, never later than today (422 `EXPENSE_DATE_IN_FUTURE`). `month = date.slice(0, 7)`. `fyCode` is the financial year **of the expense date**.
- **Numbers:** `<branch.prefixes.expense>/<fyCode>/<seq padded to 4>` (internal series, not a GST document, so the 16-character GST limit does not apply), gapless per branch × FY, taken with `nextDocumentNumber({ docType: 'expense', now: istDayBounds(date).start, start })` inside the creating transaction; start from `settings.numberSeries['expense:<fyCode>']`.
- **Idempotency:** `POST /v1/expenses` requires `Idempotency-Key`; after commit the handler answers 201 even if reading the expense back fails (M4 `respondCommitted` pattern). Edit and void use `version`.
- **Never deleted:** the model refuses `deleteOne`, `deleteMany`, `findOneAndDelete`, `replaceOne`, `findOneAndReplace` and `updateMany`; a voided expense refuses every further change.
- **Audit:** create, update (only when something changed) and void — each `recordAudit({ entityType: 'expense', … })` in the same transaction, with the business fields (`date, category, note, payee, total, mode, reference, gst, attachments (keys), link, status, void`).
- **Tax:** the amount staff enter is the **total paid** (GST included). With a GST bill: `taxable + cgst + sgst + igst === total` exactly; never both CGST/SGST and IGST; `cgst === sgst`. Rates are integer basis points from `GST_RATES_BP`.
- **Words in the UI:** "Expenses", "Add expense", "What for?", "Paid to", "How did you pay?", "Photo of the bill", "Has a GST bill?", "Before GST", "Can claim this GST back (ITC)", "Link to an order (optional)", "Void expense". GST words appear only inside the folded GST section and the admin month figures.
- Commit subjects end with `(M5 Task N)`. No deploy/infra changes.

## Decisions made in planning

| # | Decision | Why | Cost if wrong |
|---|---|---|---|
| 1 | The expense number's financial year is the **FY of the expense date**, not of the day it was typed in. A March bill entered on 2 April is `EXP/2526/…`. | The expense register for a year then lists only that year's expenses, in one series. Numbers are internal (spec §6.1), so a late entry continuing last year's series is harmless. | Switch `now` in one call to `clock.now()`; existing numbers stay. |
| 2 | **Back-dating** to any open month is allowed; future dates are refused. Changing the date on edit must stay in the same FY (else 422 `EXPENSE_FY_CHANGE`: void and add again). | Staff often enter last week's bills; the lock, not the date, is the guard. A cross-FY move would leave the number in the wrong series. | None. |
| 3 | Staff enter the **total paid**; GST is optional. With a rate, the split is **backed out of the total** with `computeAdvanceTax` (same rounding as receipt vouchers); the figures are then editable to match the paper bill. The server checks the sum exactly and, when a rate is given, each head within ₹1 of `taxHeads(taxable, rate)`; "Mixed rates" (`rateBp: null`) skips the rate check. | Staff know what they paid, not the taxable value. The ₹1 tolerance catches typing errors (₹1,800 for ₹180) without refusing a real bill rounded per line. | Tolerance is one constant in `checkExpenseTax`. |
| 4 | **CGST/SGST vs IGST**: the form defaults from the payee's state (vendor `stateCode` → GSTIN state → branch state, via `placeOfSupply`). The server stores `interState = igst > 0` from the entered heads and does **not** refuse a bill that disagrees with the payee's state. | The supplier's bill is the legal record (e.g. an online service billed from another state); refusing would block entering a real bill. | A wrongly typed head shows on the GSTR-3B summary; the accountant fixes the expense. |
| 5 | A GST bill needs the **supplier's GSTIN** (from the vendor or typed) and the bill number (≤ 16 characters) and date. `itcEligible` defaults to true; staff can switch it off. | ITC needs a GSTIN and bill reference; blocked credits (§17(5)) are an accountant's call. | Accountant to confirm defaults per category: a later `itcDefault` flag on a category is one field. |
| 6 | **Categories live in settings** as `expenseCategories: [{ key, label, active }]` with 15 defaults. Keys are **never removed** (422 `CATEGORY_REMOVED`: hide instead); labels can change. Hidden categories are refused for new expenses and kept on old ones. M6 relies on the `material_purchase` key. | Settings already has admin-only edit with audit; never-removed keys keep every old expense labelled without settings having to read expenses (no cross-module read). | Moving to a collection later is a small migration of one array. |
| 7 | New permission **`expenses.view`** (admin + operations) for reads; `expenses.write` (admin + operations) for create, edit and **void**. | Spec's future Accountant role needs read-only expenses; operations enter most bills and should fix their own mistakes (every change is audited). | If the owner wants voids admin-only: `expenses.void` in `permissions.js` + one route guard. |
| 8 | Voiding is **permanent** (no un-void); voided expenses stay listed (struck through, filter "Voided") and count zero in every figure. | Matches billing cancel semantics; "add it again" is simpler than a reversible state for staff. | — |
| 9 | One optional **link**: a garment, a batch or a whole order (the owner added order to the spec's garment/batch). Batch and order expenses are **split equally at read time** across the batch's/order's garments that are not `cancelled` (rejected ones keep their share — the money was spent), with `allocateProRata` in garment order so the parts sum exactly. Cost value = `taxable + (itcEligible ? 0 : tax)`; no GST bill → `total`. | Spec §6.3; splitting at read time stays right when garments are added to an order. | Snapshotting the split at save is one function in `costing.js`. |
| 10 | Bill photos: file purpose **`expense_bill`** (JPEG, PNG, WebP, HEIC, PDF; 10 MB; at most 5 per expense). At save, each key must start with `<branchId>/expense_bill/` and **exist in storage** (`headObject`, else 400 `ATTACHMENT_NOT_UPLOADED`); its type and size are stored from the stored object. Reading needs `expenses.view` on a saved expense's key, or `expenses.write` for a not-yet-saved upload (the form preview). | Spec §10.3; checking the object exists stops an expense saved with a photo that never arrived. | — |
| 11 | The web **shrinks photos** (JPEG/PNG/WebP) to ≤ 2000 px on the long side, JPEG quality 0.8, before upload; HEIC and PDF go as they are. Upload starts as soon as the photo is taken, while staff fill the rest. | A 6 MB phone photo on mobile data would blow the 20-second budget. | Turn shrinking off: one call in `BillPhotos`. |
| 12 | **Payee snapshot**: `{ vendorId, name, gstin, stateCode }` is copied onto the expense; later vendor edits do not change past expenses. Free-text payees are offered again from recent expenses ("Recent"). | Past expenses must keep the GSTIN they were claimed under; recent names make the second entry for the same shop one tap. | — |
| 13 | **Indexes:** `by_date (branchId, date, _id)` serves month lists, the month summary, M8 tile 10 and the register (a month is a date range); `by_category (branchId, category, date, _id)`; `by_vendor`, `by_order`, `by_garment`, `by_batch` partial; `attachments (branchId, attachments.key)`; `number_unique (branchId, fyCode, number)`. Garments gain `batch (branchId, batchId)` partial. | One range index answers every month question; no stored totals to drift. | Add a `(branchId, month, status)` index if M8 explain shows otherwise. |
| 14 | No `jobs.js` in M5: nothing runs on a schedule. "GST bills without a photo" is a number in the month summary with a filter, not a reminder. | Avoids a notification nobody asked for; M8's monthly GST pack covers the month-end nudge. | A weekly digest is one job file. |
| 15 | Payment modes reuse `PAYMENT_MODES` (cash, UPI, card, bank transfer). **No unpaid/credit expenses** (payables). | Spec §6.1 records money paid. | Payables are a later feature. |
| 16 | Nav "Expenses" (`IconReceiptRupee`, phone `more`); the phone bottom bar is unchanged (operations keep Home, Orders, Bills, Customers). The Home page gets an **"Add expense"** button for `expenses.write`, and `/expenses` has a fixed "Add expense" button at the bottom on phones. | Two taps from anywhere without displacing Bills. | Nav order only. |
| 17 | `createExpense(branchId, input, actor, { session, source })` can join a caller's transaction (`source: 'purchase'` for M6 stock receiving; default `'manual'`). | Spec §6.2 step 3: receiving stock creates the material purchase expense in one transaction. | — |

## Review Focus

1. **Double tap on "Save expense", or a save that fails half way** — exactly one expense, one number; the next expense gets the next number. → Task 3 tests `saving twice with one key makes one expense` and `an aborted save leaves no gap in the numbers`.
2. **A locked month** — creating, editing or voiding an expense dated in it, or moving an expense into or out of it, is refused with 422 `PERIOD_LOCKED` and writes nothing (no number, no audit). → Task 4 tests `a locked month refuses every expense write` and `an expense cannot be moved into or out of a locked month`.
3. **GST figures** — the split backed out of the total always adds up to the total; CGST/SGST are equal halves; a typed head that disagrees with the rate by more than ₹1 is refused; IGST is stored as inter-state. → Task 1 test `the split from a total always adds up`; Task 3 test `tax that does not add up or does not match the rate is refused`.
4. **Designers never see costs** — every expense route is 403 for a designer, a bill photo's URL is "not found", and order/garment responses carry no expense field. → Task 7 tests `designers are refused every expense route`, `a designer cannot open a bill photo` and `order and garment responses carry no expense figures`.
5. **Batch and order expenses in garment cost** — ₹1,000 on a batch of three gives 33334/33333/33333 paise; a voided expense counts nothing; GST is added only when ITC cannot be claimed; a cancelled garment gets no share. → Task 5 tests `a batch expense splits equally and sums exactly`, `GST is part of the cost only when it cannot be claimed` and `cancelled garments get no share`.

Check the bill."

  - `expenseCost(expense) → paise` — `0` when `status === 'voided'`; no `gst` → `total`; else `taxable + (itcEligible ? 0 : cgst + sgst + igst)`.
